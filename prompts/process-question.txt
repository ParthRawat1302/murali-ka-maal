ALGOWEB: HOW TO PROCESS A QUESTION THE USER GIVES YOU
=====================================================

Use this whenever the user hands you a question to add to AlgoWeb, in any form:
  - a LeetCode link (usually from a teacher's email),
  - a photo of class notes (board/notebook),
  - a test question (text or photo),
  - DomJudge problem text,
  - any mix of these, possibly with the teacher's solution.

The website has NO LLM. You (Claude) do the thinking, then write a JSON file and run the import script.
Everyone in the class sees what you add, so accuracy matters more than speed.


STEP 0: GET THE METADATA
------------------------
Every question needs:
  source_type   email | test | class_notes | domjudge | other
  source_label  test name ("Midterm 1"), email subject, lecture name … (optional for class notes)
  source_date   YYYY-MM-DD (the class/test/email date, NOT today, unless it is today)
Rules of thumb:
  - LeetCode link with nothing else  -> source_type "email"
  - photo of notes                   -> "class_notes" (date is essential)
  - "test"/"quiz"/"exam" mentioned   -> "test" + test name as source_label
  - DomJudge text                    -> "domjudge"
If the date or test name is missing and you can't infer it, ASK once (one short question) before importing.
If the user says who it's for, pass --as <username> (see config/users.json); otherwise it goes to the admin.


STEP 1: UNDERSTAND THE QUESTION
-------------------------------
- Transcribe photos carefully: the task, input/output format, every example, constraints, and any
  solution/approach the teacher wrote (code, dry-run tables, diagrams).
- One photo may contain several questions; each becomes its own import file.
- If part of the photo is unreadable or ambiguous, say what you could not read and ask; never guess
  numbers in examples or constraints.


STEP 2: CHECK IT ISN'T ALREADY IN ALGOWEB
-----------------------------------------
  npx tsx scripts/find-question.ts <a few title words | leetcode url>
If it's already there (same problem), tell the user and stop, unless they want it added again
(e.g. it was given in a test too). Then use --allow-duplicate on import.


STEP 3: LOOK FOR THE SAME PROBLEM ON LEETCODE (ALWAYS DO THIS FIRST)
--------------------------------------------------------------------
1. Think of candidate LeetCode problems from what you know, and/or WebSearch with a distinctive phrase,
   e.g. "leetcode <core task in a few words>".
2. Verify each candidate against the real statement:
     npx tsx scripts/leetcode.ts <slug-or-url> [<slug2> …]
3. Decide:
   SAME: same task, same input/output meaning, examples agree (variable names, wording,
         or 0/1-indexing presentation may differ). -> use that LeetCode problem (Step 4A).
   VARIANT: the teacher changed the task (returns a count instead of a list, extra constraint,
         different operation, combined two problems…). -> NOT the same. Write it yourself (Step 4B),
         and add one line at the end of the statement:
         <p><em>Similar to <a href="https://leetcode.com/problems/<slug>/">LeetCode #N. Title</a> (differs in: …)</em></p>
   NONE: nothing close. -> Step 4B.
When unsure between SAME and VARIANT, choose VARIANT and say why in your reply.


STEP 4A: IT IS A LEETCODE PROBLEM
---------------------------------
Write a minimal JSON. The import script fetches title, difficulty, topics and the full statement
from LeetCode automatically:
  {
    "leetcode_url": "https://leetcode.com/problems/<slug>/",
    "source_type": "email",
    "source_label": null,
    "source_date": "2026-10-08",
    "topics": [],                      // extra topics from the teacher's solution, if any
    "notes": [ … teacher's solution, see Step 5 … ]
  }
Do not write statement_html for LeetCode problems (the official one is fetched).
For a premium (paid-only) problem, the statement is hidden. Write the statement yourself as in 4B
and keep the leetcode_url.


STEP 4B: NOT ON LEETCODE: WRITE THE QUESTION (LeetCode style)
-------------------------------------------------------------
Title: short and descriptive, Title Case, like a LeetCode title ("Minimum Swaps to Group Ones").
Difficulty: judge like LeetCode would:
  easy   = one standard idea, direct implementation (single pass, basic hashing, simple recursion)
  medium = needs a known technique applied with some insight (DP, BFS/DFS variants, two pointers,
           binary search on answer, heaps, monotonic stack)
  hard   = combines techniques, non-obvious insight, or a tricky optimisation
Topics: use LeetCode tag names exactly (Array, String, Hash Table, Dynamic Programming, Math, Sorting,
  Greedy, Depth-First Search, Breadth-First Search, Binary Search, Tree, Binary Tree, Binary Search Tree,
  Matrix, Two Pointers, Bit Manipulation, Stack, Queue, Heap (Priority Queue), Graph, Prefix Sum,
  Simulation, Design, Counting, Backtracking, Sliding Window, Union Find, Linked List, Monotonic Stack,
  Trie, Recursion, Divide and Conquer, Memoization, Topological Sort, Segment Tree, Shortest Path,
  Bitmask, Combinatorics, Number Theory, String Matching, Geometry, Game Theory, Monotonic Queue,
  Minimum Spanning Tree, Binary Indexed Tree, Doubly-Linked List, Hashing).
  Pick them from how the problem is SOLVED (the teacher's solution if given), not just from the story.
  2–4 topics is typical. Only invent a new topic name if none of these fit.

statement_html structure:
  <p>Problem description. Use <code>nums</code> for identifiers and <sup> for powers.</p>
  <p>More paragraphs / a <ul> if the rules have several parts.</p>

  <p><strong>Example 1:</strong></p>
  <img src="asset:<name>-ex1.svg" alt="…">          <- only when a picture helps (see diagrams)
  <pre><code class="language-plaintext">Input: nums = [2,7,11,15], target = 9
Output: [0,1]
Explanation: nums[0] + nums[1] == 9.</code></pre>

  <p><strong>Example 2:</strong></p> …           <- at least 2 examples; include an edge case

  <p><strong>Constraints:</strong></p>
  <ul><li><p><code>1 &lt;= n &lt;= 10<sup>5</sup></code></p></li> …</ul>

  (optional) <p><strong>Follow-up:</strong> …</p>

- Escape < > & inside HTML as &lt; &gt; &amp;.
- Keep the teacher's examples. If there are fewer than 2, add your own.
- VERIFY EVERY EXAMPLE OUTPUT: write a quick reference solution (node or python in the scratchpad),
  run it on all examples, and make sure the outputs match exactly. Fix the example or your
  understanding if they don't.
- If constraints weren't given, choose reasonable ones that match the intended complexity, and
  mention in your reply that they were assumed.

DIAGRAMS: add an SVG wherever LeetCode would show a picture:
  trees, graphs, grids/matrices, linked lists, intervals on a number line, arrays with pointers/windows,
  before/after states of an operation.
  - Save as content/imports/assets/<date>-<slug>-<what>.svg and reference it as asset:<filename>
    (list it in "assets": { "<filename>": "assets/<filename>" }).
  - White background rect, width 300–600px, viewBox set, Arial/sans-serif 14–16px labels.
  - Nodes: circles r≈20, fill #fff4e0, stroke #f59e0b (2px); edges #555 2px; arrows with a marker.
  - Arrays: row of boxes 40×40 with values centred and small grey indices underneath; highlight the
    important cells with fill #fff4e0 / stroke #f59e0b; pointers as labelled arrows below.
  - Grids: square cells, walls/blocked = #555 fill, path = #00b8a3.
  - Only draw what's in the example; the picture must match the example data exactly.
  - Place each diagram right after its "Example N:" heading, before the Input/Output block.


STEP 5: NOTES (TEACHER'S SOLUTION)
----------------------------------
If the teacher gave a solution/approach, add it as a public note:
  "notes": [{ "title": "Teacher's solution", "visibility": "public", "html": "…" }]
- Short explanation of the idea in your words, then the code exactly as given (fix only obvious
  transcription slips) in <pre><code class="language-cpp|java|python|javascript">…</code></pre>.
- Include complexity: <p><strong>Time:</strong> O(n) · <strong>Space:</strong> O(1)</p>.
- Dry-run tables → <table>. Board diagrams → redraw as SVG (asset) if useful.
- If the user gave the photo as a file path, also attach it in a note titled "Original class notes"
  (<img src="asset:<file>">) so people can check the source.
- Don't invent a "teacher's solution". If none was given, add no note (or a note titled
  "Approach (Claude)" only if the user asks for one).


STEP 5B: INTENDED METHOD (WHAT THE TEACHER WANTS IT SOLVED WITH)
----------------------------------------------------------------
Many questions can be solved several ways; the teacher gives them to practise the topic being taught.
For every question from an email / class / test, record that topic in content/intents.json under the
group for that source (source_type, source_label, source_date), keyed by LeetCode slug or exact title:
  - Use the email's topic (subject line, "This week: binary search", the ?envId=… in the LeetCode link,
    e.g. envId=binary-indexed-tree -> "Binary Indexed Tree").
  - If the question has that topic, use it. If not, pick the closest topic the question DOES have.
  - Usually ONE topic; at most two when the email explicitly names both. Don't highlight much.
  - If the question is already listed (Step 2), don't import it again: just add it to the new
    email's group in content/intents.json, possibly with a different intended topic.
Then run:  npx tsx scripts/sync-intents.ts
These topics are shown first and softly highlighted in the question's topic chips.


STEP 6: WRITE THE FILE AND IMPORT
---------------------------------
- File: content/imports/<source_date>-<short-slug>.json   (format: content/imports/README.md)
- Run:  npx tsx scripts/import-question.ts content/imports/<file>.json [--as <username>] [--allow-duplicate]
  (In PowerShell, call npx tsx directly; "npm run x -- --flag" drops flags.)
- Re-running the same file updates the same question (matched by title + source + date), so fix and
  re-run freely.
- If it fails with "Duplicate LeetCode problem", report the existing entry and ask the user.


STEP 7: REPORT BACK (SHORT)
---------------------------
For each question: title · difficulty · topics · source/date · "LeetCode #N (same problem)" or
"written up (similar to #N, differs in …)" or "written up (no LeetCode match)" · the /q/<id> path
printed by the script · anything assumed (constraints, unreadable parts).
